# Delivery semantics — prior-art recon for the monitor/subscriber protocol

2026-09-21. `[SRC]` = quoted/closely paraphrased from the cited page, fetched today; `[DERIVED]` = our reasoning. Kafka's unversioned `kafka.apache.org/documentation` is a JS redirect stub; the current pages are under `/43/` (Kafka 4.3).

## 1. Kafka

**Offsets, position.** `[SRC]` "the position of a consumer in each partition is just a single integer, the offset of the next message to consume"; "a consumer can deliberately rewind back to an old offset and re-consume data" — https://kafka.apache.org/43/design/design/#the-consumer. `[SRC]` "events are not deleted after consumption" — https://kafka.apache.org/intro. `[SRC]` Javadoc: "The *position* of the consumer gives the offset of the next record that will be given out." "The *committed position* is the last offset that has been stored securely. Should the process fail and restart, this is the offset that the consumer will recover to." — https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html. `[SRC]` "The offset for a message never changes. It is the permanent identifier for a position in the log." — https://kafka.apache.org/43/design/design/#log-compaction.

**Commit.** `[SRC]` `enable.auto.commit` default `true`: "the consumer's offset will be periodically committed in the background"; `auto.commit.interval.ms` 5000 — https://kafka.apache.org/43/generated/consumer_config.html. `[SRC]` Javadoc: with auto-commit, records are "considered consumed" once returned by `poll()`; with manual control `commitSync()` blocks until done or timeout, `commitAsync()` returns immediately with a callback. Commit only after processing when consumption "is coupled with some processing logic"; hazard: a crash "after the insert into the database but before the commit" means the successor "would repeat the insert."

**Delivery guarantees, exact wording.** `[SRC]` "*At most once* – Messages may be lost but are never redelivered. *At least once* – Messages are never lost but may be redelivered. *Exactly once* – Each message is processed once and only once." Consumer options: "It can read the messages, then save its position in the log, and finally process the messages" (at-most-once); "It can read the messages, process the messages, and finally save its position" (at-least-once). "Kafka guarantees at-least-once delivery by default, and allows the user to implement at-most-once delivery by disabling retries on the producer and committing offsets in the consumer prior to processing a batch of messages." — https://kafka.apache.org/43/design/design/#message-delivery-semantics. `[DERIVED]` Kafka's phrase for "process then commit" is that sentence: *read, process, then save position*.

**Exactly-once parts.** `[SRC]` "the broker assigns each producer an ID and deduplicates messages using a sequence number that is sent by the producer along with every message"; transactions write to multiple partitions so "either all messages are successfully written or none of them are" (same page). `[SRC]` Producer `enable.idempotence` default `true`: "exactly one copy of each message is written in the stream"; `transactional.id` null → "limited to idempotent delivery" — https://kafka.apache.org/43/generated/producer_config.html. `[SRC]` `isolation.level` default `read_uncommitted`; `read_committed`: "consumer.poll() will only return transactional messages which have been committed … Messages will always be returned in offset order" (consumer_config).

**Groups, assignment.** `[SRC]` "each partition is assigned to exactly one consumer in the group" (javadoc); membership change → *rebalance*. `partition.assignment.strategy` default `RangeAssignor, CooperativeStickyAssignor`; `group.instance.id` → "static member" (consumer_config).

**`auto.offset.reset`.** `[SRC]` "What to do when there is no initial offset in Kafka or if the current offset does not exist any more on the server": `earliest`, `latest` (default), `by_duration:<d>`, `none` ("throw exception") (consumer_config). `[SRC]` A read at a missing offset raises `OutOfRangeException` — https://kafka.apache.org/43/implementation/log/.

**Retention, compaction.** `[SRC]` `retention.ms` default 7 days: "This represents an SLA on how soon consumers must read their data." `cleanup.policy` `delete` | `compact` ("retains the latest value for each key") | `delete,compact`; `delete.retention.ms` (tombstones) 1 day — https://kafka.apache.org/43/generated/topic_config.html. `[SRC]` `offsets.retention.minutes` default 10080: committed offsets expire after the group has been empty that long — https://kafka.apache.org/43/generated/kafka_config.html. `[SRC]` Compaction "will always retain at least the last known value for each message key"; "Any consumer progressing from the start of the log will see at least the final state of all records in the order they were written" (design/#log-compaction). `[DERIVED]` Lagging chain: cursor older than retention → `OutOfRangeException` → `auto.offset.reset` policy.

**Slow consumer loses assignment.** `[SRC]` `max.poll.interval.ms` 300000: "If poll() is not called before expiration of this timeout, then the consumer is considered failed and the group will rebalance in order to reassign the partitions to another member." `session.timeout.ms` 45000 / `heartbeat.interval.ms` 3000: no heartbeat → "the broker will remove this client from the group and initiate a rebalance" (consumer_config). Javadoc: the client "will proactively leave the group so that another consumer can take over its partitions."

**Share groups (Kafka 4.x).** `[SRC]` "consumers in a share group cooperatively consume records, and partitions may be assigned to multiple consumers"; "Records are acknowledged individually"; each carries "a time-limited acquisition lock"; outcomes: accept, "release the record, making it available for another delivery attempt", "reject the record, indicating it's unprocessable"; lock expiry → redelivery — https://kafka.apache.org/43/design/design/#share-groups. `[SRC]` `group.share.record.lock.duration.ms` 30000; `group.share.delivery.count.limit` 5 (kafka_config). `[DERIVED]` Kafka's own vocabulary for per-record lease + redelivery + attempt cap.

## 2. Kubernetes watch and Lease

Source https://kubernetes.io/docs/reference/using-api/api-concepts/ unless noted.

- `[SRC]` "A resource version is an opaque string … Clients must not assume resource versions are numeric or collatable." Monotonic "only … within the scope of a single apiserver instance and only per resource type."
- `[SRC]` `GET …/pods?watch=true&resourceVersion=10245` → `{"type": "ADDED"|"MODIFIED"|"DELETED", "object": …}`. "The watch request may timeout due to inactivity, but will resume from where it left off."
- `[SRC]` "When the resourceVersion becomes too old … the server will send an HTTP 410 (Gone) status code. At that point, the client must … clear its local cache, and perform a list query to bootstrap the watch with a new resourceVersion." ERROR event: `kind: Status, message: "too old resource version: 123", reason: "Expired", code: 410`.
- `[SRC]` `allowWatchBookmarks`: "a synthetic BOOKMARK event just before closing a watch connection due to timeout … All events after the bookmark have happened after that resourceVersion."
- `[SRC]` `sendInitialEvents=true` "can only be set when resourceVersionMatch=NotOlderThan and a specific resourceVersion value is provided"; initial state ends with a BOOKMARK annotated `k8s.io/initial-events-end: "true"`. Watch start: unset → most recent; `"0"` → all current objects, then live; exact → from there. `resourceVersionMatch`: `Exact` (mismatch → 410), `NotOlderThan` (default).
- `[SRC]` "The server may close a watch at any time … resume … using the resourceVersion from the last received object"; "The default timeout is 5-10 minutes."
- `[SRC]` Lease `coordination.k8s.io/v1`: `holderIdentity` "identity of the holder of a current lease"; `leaseDurationSeconds` "a duration that candidates for a lease need to wait to force acquire it. This is measured against the time of last observed renewTime"; `acquireTime`; `renewTime` "when the current holder of a lease has last updated the lease"; `leaseTransitions` "number of transitions of a lease between holders" — https://kubernetes.io/docs/reference/kubernetes-api/cluster-resources/lease-v1/
- `[SRC]` Leases "lock shared resources and coordinate activity between members of a set" — https://kubernetes.io/docs/concepts/architecture/leases/. Leader renews `renewTime` (e.g. every `leaseDurationSeconds ÷ 2`); "When the Lease does not exist or has expired (current time > renewTime + leaseDurationSeconds), candidate instances attempt to update the Lease with their identity"; "optimistic concurrency control via the object's resourceVersion: only one update succeeds" — https://kubernetes.io/docs/concepts/cluster-administration/coordinated-leader-election/
- `[SRC]` client-go: "does not guarantee that only one client is acting as a leader (a.k.a. fencing)"; knobs `LeaseDuration`, `RenewDeadline`, `RetryPeriod` — https://pkg.go.dev/k8s.io/client-go/tools/leaderelection

## 3. MQTT 5.0

Spec https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html (§ numbers); HiveMQ Essentials for gloss.

- `[SRC]` §4.3: QoS 0 "At most once delivery", QoS 1 "At least once delivery" (PUBACK, duplicates), QoS 2 "Exactly once delivery" (PUBREC/PUBREL/PUBCOMP); broker downgrades to the subscriber's QoS — https://www.hivemq.com/blog/mqtt-essentials-part-6-mqtt-quality-of-service-levels/
- `[SRC]` §3.3.1.3 RETAIN: "the Server MUST replace any existing retained message for this topic and store the Application Message [MQTT-3.3.1-5]"; "When a new non-shared Subscription is made, the last retained message, if any, on each matching topic name MUST be sent to the subscriber [MQTT-3.3.1-7]"; empty payload clears [MQTT-3.3.1-6]. Gloss "The broker stores the last retained message and the corresponding QoS for that topic" — https://www.hivemq.com/blog/mqtt-essentials-part-8-retained-messages/. `[DERIVED]` "Last known good value" is community wording, not spec text.
- `[SRC]` §3.1.2.11.2 Session Expiry Interval: 0/absent → "the Session ends when the Network Connection is closed"; `0xFFFFFFFF` → "the Session does not expire"; "MUST store the Session State after the Network Connection is closed if the Session Expiry Interval is greater than 0 [MQTT-3.1.2-23]."
- `[SRC]` §4.1 server Session State: subscriptions, "QoS 1 and QoS 2 Application Messages pending transmission to the Client", unacknowledged QoS 1/2, "Optionally, QoS 0 Application Messages pending transmission", Will Message + Will Delay Interval.
- `[SRC]` §4.7.1.2 `#` "matches zero or more levels within a topic name"; §4.7.1.3 `+` "matches exactly one topic level."
- `[SRC]` §4.8.2 `$share/{ShareName}/{filter}`; the Server sends a matching message to "one of the subscribed Sessions" only; gloss "competing consumers" — https://www.hivemq.com/blog/mqtt5-essentials-part7-shared-subscriptions/
- `[SRC]` §3.1.2.5 Will: "MUST be published after the Network Connection is subsequently closed and either the Will Delay Interval has elapsed or the Session ends, unless … deleted by the Server on receipt of a DISCONNECT packet with Reason Code 0x00." Gloss — https://www.hivemq.com/blog/mqtt-essentials-part-9-last-will-and-testament/

## 4. AMQP 0-9-1 / RabbitMQ

- `[SRC]` Automatic ("fire-and-forget", "considered unsafe") vs manual acknowledgement. Delivery tags: "monotonically growing positive integers" per channel. `basic.ack`; `basic.nack` (extension, `multiple`); `basic.reject`. `requeue=true` → "the broker will requeue the delivery"; `false` → "discarded or dead-lettered". "When a message is requeued, it will be placed to its original position in its queue, if possible." On channel loss "any delivery (message) that was not acked is automatically requeued" with `redelivered=true`. Prefetch (`basic.qos`): "the max number of unacknowledged deliveries that are permitted on a channel" — https://www.rabbitmq.com/docs/confirms
- `[SRC]` Acknowledgement timeout default 30 min (`consumer_timeout`) → channel closed `PRECONDITION_FAILED`, requeue. Exclusive consumer vs Single Active Consumer (auto failover) — https://www.rabbitmq.com/docs/consumers
- `[SRC]` Dead-letter triggers: nack/reject `requeue=false`, TTL, length limit, quorum `delivery-limit`; `x-dead-letter-exchange`; `x-death` {`count`, `reason` ∈ `rejected|expired|maxlen|delivery_limit`, `queue`, `time`} — https://www.rabbitmq.com/docs/dlx

## 5. Server-Sent Events

- `[SRC]` `id`: "If the field value does not contain U+0000 NULL, then set the last event ID buffer to the field value." `retry`: "If the field value consists of only ASCII digits, then interpret the field value as an integer in base ten, and set the event stream's reconnection time to that integer." Reconnect: "If the EventSource object's last event ID string is not the empty string … Set (`Last-Event-ID`, lastEventIDValue) in request's header list." HTTP 204 stops reconnecting; a `:` comment "every 15 seconds or so" defeats legacy proxies — https://html.spec.whatwg.org/multipage/server-sent-events.html.
- `[SRC]` MCP 2026-07-28 changelog §9: "Remove SSE stream resumability and message redelivery (the `Last-Event-ID` header and SSE event IDs) from the Streamable HTTP transport" — https://modelcontextprotocol.io/specification/2026-07-28/changelog

## 6. Idempotency

- `[SRC]` draft-ietf-httpapi-idempotency-key-header-07 (2025-10-15; datatracker status *expired*): "Idempotency-Key is an Item Structured Header. Its value MUST be a String"; "RECOMMENDED that a UUID or a similar random identifier be used"; the key "MUST NOT be reused with another request with a different request payload." Completed duplicate → "respond with the result of the previously completed operation, success or an error"; in-flight duplicate → "resource conflict error". Errors: 400 missing key; 422 "reuse an idempotency key with a different request payload"; 409 "retried before the original request completed". Server may compute an *idempotency fingerprint* of the payload — https://www.ietf.org/archive/id/draft-ietf-httpapi-idempotency-key-header-07.html (status: https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)
- `[SRC]` Stripe: saves "the resulting status code and body of the first request … Subsequent requests with the same key return the same result, including 500 errors." ≤ 255 chars, V4 UUIDs, pruned after ≥ 24 h; mismatched parameters → error; POST only — https://docs.stripe.com/api/idempotent_requests

## 7. Standard Webhooks

Source https://raw.githubusercontent.com/standard-webhooks/standard-webhooks/main/spec/standard-webhooks.md (standardwebhooks.com/spec returned 404 today).

- `[SRC]` `webhook-id` "the unique webhook identifier"; `webhook-timestamp` "integer unix timestamp (seconds since epoch)"; `webhook-signature` "the signature(s) of this webhook", "space delimited" for zero-downtime rotation.
- `[SRC]` Signed content `msg_id.timestamp.payload`; HMAC-SHA256, `v1,` prefix, base64, secret `whsec_`; ed25519 `v1a,`.
- `[SRC]` The id "remains the same no matter how many times a webhook that has failed is retried. The ID is often used as an idempotency key"; the attempt timestamp changes per retry and is "meant to prevent replay attacks". Verify `webhook-timestamp` "within some allowable tolerance" (no normative number; the example stores ids "in redis for 5 minutes").
- `[SRC]` "retry … following a retry schedule spanning multiple days, with an exponential backoff" plus jitter; example: immediately, 5 s, 5 m, 30 m, 2 h, 5 h, 10 h, 14 h, 20 h, 24 h; on persistent failure notify out-of-band and disable the endpoint. Success = `2xx`; receiver `410 Gone` → "Sender should disable the webhook endpoint"; honour `retry-after`.

## Semantics we adopt, named

| Our need | Established term (source) | Behaviour we specify |
|---|---|---|
| Durable cursor | Kafka *committed position* (javadoc); K8s `resourceVersion` (api-concepts) | One committed seq per (subscriber, monitor) = *next* seq to deliver, stored server-side. Integer and collatable, unlike K8s — say so. |
| Ack after processing | Kafka "read, process, then save position" = at-least-once; RabbitMQ manual `basic.ack` | Ack only after side effects complete; the guarantee is **at-least-once**, in Kafka's words. |
| Redelivery on crash | Kafka "recover to committed position"; RabbitMQ auto-requeue + `redelivered`; share-group lock expiry | Uncommitted events redeliver from the cursor with a `redelivered` flag. |
| Idempotence by seq | Kafka idempotent producer (PID + sequence); Idempotency-Key draft (replay / 409 / 422); `webhook-id` | Monotonic seq per monitor; dedupe on `(monitor, seq)`; re-ack of a committed seq is a no-op returning the prior result. |
| Head vs filtered head | Kafka log-end offset vs position; K8s list RV vs watch selector; MQTT `+`/`#` filters | Expose `head` and `lag = head − cursor`; a filter never renumbers — filtered subscribers still commit the monitor's seq. **Conflict:** Kafka offsets are per partition; ours per monitor. |
| Cursor never moves backwards | Kafka "The offset for a message never changes"; RabbitMQ tags "monotonically growing" | Reject a commit below the stored cursor unless an explicit `seek` (Kafka `seek`/`seekToBeginning`). |
| Lagging consumer, data compacted | Kafka `OutOfRangeException` + `auto.offset.reset`; K8s `410 Gone`, `reason: Expired` → relist | Cursor older than retention → `EXPIRED` (410 semantics) → **relist from retained state**, then resume; policy field mirrors `earliest|latest|none`. |
| Lease with expiry and renewal | K8s Lease fields; MQTT Session Expiry Interval | Same five fields; expired when `now > renewTime + leaseDurationSeconds`; renew at ≤ duration/2; CAS on lease version. |
| Exclusive claim | Kafka share-group *acquisition lock* + `delivery.count.limit`; RabbitMQ Single Active Consumer; MQTT `$share/` | Time-limited lock per work item; `release`/`reject` outcomes; attempt cap, then dead-letter. |
| Retained state beside the stream | MQTT retained message; Kafka compaction ("last known value for each message key"); K8s `sendInitialEvents` + `initial-events-end` bookmark | Each monitor keeps a compacted **state** doc sent to a new/relisting subscriber before the stream, closed by a synthetic bookmark. |
| Dead subscriber retirement | Kafka `max.poll.interval.ms` "considered failed … rebalance", `offsets.retention.minutes`; MQTT Session Expiry + Will; RabbitMQ `consumer_timeout` | No poll/renew within expiry → claims released, cursor kept for a bounded period then dropped, a *will* event published. |
| Reconnect over HTTP | SSE `id:` + `Last-Event-ID`, `retry:` | Streams send `id: <seq>`; resume from `Last-Event-ID`. MCP 2026-07-28 dropped this from its transport; we keep it in ours. |
| Push to non-polling subscribers | Standard Webhooks headers, multi-day backoff, `410 Gone` | Reuse the three headers and signed `id.timestamp.payload`; receiver 410 retires the subscription. |

**Named conflicts.** `[DERIVED]` (1) Kafka commits are per partition and group; ours per subscriber and monitor — no partitions, so "rebalance" reduces to lease transfer. (2) K8s `resourceVersion` is opaque; our seq is ordered — do not name it `resourceVersion`. (3) Kafka's `enable.auto.commit=true` default leaks toward at-most-once; ours is manual commit. (4) MQTT QoS 2 is hop-level; our exactly-once is idempotent processing keyed by seq, as Kafka frames it. (5) The Idempotency-Key draft is expired at IETF; cite Stripe as practice, the draft as vocabulary.
