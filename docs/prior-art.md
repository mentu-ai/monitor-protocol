# Prior-art recon: epistemic layer over pub/sub

Date: 2026-09-21. Fetched live from the spec sources named at each fact. `[SRC]` = quoted or read directly from the cited page; `[DERIVED]` = reasoned from `[SRC]` facts. Where two fetches disagreed, the raw file won and the disagreement is recorded.

## 1. CloudEvents (CNCF)

**Versions.** Repo README: core spec, JSON/Avro/Protobuf formats and HTTP/AMQP/Kafka/MQTT/NATS bindings are `v1.0.2` released with a `WIP` branch; WebSockets binding, XML format and **Subscriptions** are `WIP only`; CESQL is `v1.0.0`. `[SRC]` https://github.com/cloudevents/spec. The `main` core spec file self-identifies as `1.0.3-wip`; the `specversion` attribute value stays `"1.0"`. `[SRC]` https://raw.githubusercontent.com/cloudevents/spec/main/cloudevents/spec.md

**REQUIRED attributes** `[SRC]` (same URL): `id` (String, non-empty) — "Producers MUST ensure that `source` + `id` is unique for each distinct event"; `source` (URI-reference, non-empty, absolute URI recommended); `specversion` (String, `"1.0"`); `type` (String, non-empty, "SHOULD be prefixed with a reverse-DNS name").

**OPTIONAL attributes** `[SRC]`: `datacontenttype` (RFC 2046 string), `dataschema` (URI), `subject` (String), `time` (Timestamp, RFC 3339).

**Extension attributes** `[SRC]`: "MUST follow the same naming convention and use the same type system as standard attributes"; names "MUST consist of lower-case letters [a-z] or digits [0-9]", "SHOULD start with a letter", "MUST be at least one character in length, and SHOULD NOT exceed 20 characters". Type system: Boolean, Integer, String, Binary, URI, URI-reference, Timestamp. No nested/map types. `[DERIVED]` Our tier/horizon/verification fields, if carried as CE extensions, must be flat scalars with lowercase names ≤ 20 chars, e.g. `tier`, `horizon`, `seq`, `monitor`.

**Ordering / delivery / dedup** `[SRC]`: the core spec has no ordering or delivery-guarantee text. Dedup: "If a duplicate event is re-sent (e.g. due to a network error) it MAY have the same `id`. Consumers MAY assume that Events with identical `source` and `id` are duplicates."

**JSON event format** `[SRC]` https://raw.githubusercontent.com/cloudevents/spec/main/cloudevents/formats/json-format.md: media type `application/cloudevents+json`; binary data "MUST be represented as a JSON string expression containing the Base64 encoded binary value, and use the member name `data_base64`"; JSON data uses member `data`, "stored directly as a JSON value, rather than as an encoded JSON document represented as a string"; "the presence of the `data` and `data_base64` members is mutually exclusive"; "Extensions MUST be serialized as a top-level JSON property"; missing `datacontenttype` → "proceed as if it were set to `application/json`". **Batch**: "The outermost JSON element is a JSON Array" of events, media type `application/cloudevents-batch+json`.

**HTTP binding** `[SRC]` https://raw.githubusercontent.com/cloudevents/spec/main/cloudevents/bindings/http-protocol-binding.md: **binary mode** — data is the body, `datacontenttype` ↔ `Content-Type`, "All CloudEvents context attributes, including extensions, MUST be mapped to HTTP headers with the same name as the attribute name but prefixed with `ce-`" (`ce-id`, `ce-specversion`, `ce-time`); **structured mode** — body `application/cloudevents+json; charset=UTF-8`; **batched mode** — body `application/cloudevents-batch+json`.

**Extensions** `[SRC]`:
- Distributed tracing (https://raw.githubusercontent.com/cloudevents/spec/main/cloudevents/extensions/distributed-tracing.md): `traceparent` (String, REQUIRED, non-empty, W3C Trace Context §3.2) and `tracestate` (String, OPTIONAL).
- Sequence (https://raw.githubusercontent.com/cloudevents/spec/main/cloudevents/extensions/sequence.md): single attribute `sequence` (String, REQUIRED when used) "MUST be a non-empty lexicographically-orderable string", "RECOMMENDED as monotonically increasing and contiguous"; "The `sequence` with a lower lexicographical value comes first"; comparable only within one `source`. There is **no `sequencetype`** attribute in the current file (older drafts had one).
- Dataref (https://raw.githubusercontent.com/cloudevents/spec/main/cloudevents/extensions/dataref.md): `dataref` (URI-reference), the "Claim Check Pattern"; `data` and `dataref` may coexist.

**Subscriptions API** `[SRC]` https://raw.githubusercontent.com/cloudevents/spec/main/subscriptions/spec.md — version `0.1-wip`. Subscription object: `id` (String, set by the manager), `source` (URI-reference, OPTIONAL), `types` (Array of Strings, OPTIONAL), `config` (Map, OPTIONAL), `filters` (Array of filter expressions, OPTIONAL), `sink` (URI, REQUIRED: "The address to which events MUST be sent"), `sinkcredential` (Map, OPTIONAL; `credentialtype` ∈ `PLAIN`/`ACCESSTOKEN`/`REFRESHTOKEN`, fields `identifier`, `secret`, `accesstoken`, `accesstokenexpiresutc`, `accesstokentype`, `refreshtoken`, `refreshtokenendpoint`), `protocol` (String, REQUIRED; `AMQP`, `MQTT3`, `MQTT5`, `HTTP`, `KAFKA`, `NATS`), `protocolsettings` (Map, OPTIONAL; HTTP: `headers`, `method`; MQTT: `topicname`, `qos`, `retain`, `expiry`, `userproperties`; AMQP: `address`, `linkname`, `sendersettlementmode`, `linkproperties`; KAFKA: `topicname`, `partitionkeyextractor`, `clientid`, `acks`; NATS: `subject`).
  Filter dialects, JSON shape `{ "<dialect>": { ... } }`: REQUIRED `exact`, `prefix`, `suffix` (each maps attribute name → value, case-sensitive), `all`, `any`, `not`; OPTIONAL `sql` (a CESQL expression string). Manager operations: Create (SHOULD), Retrieve (MUST), Query/list (OPTIONAL), Update (OPTIONAL), Delete (SHOULD); HTTP binding sketched as `POST /subscriptions`, `GET|PUT|DELETE /subscriptions/{id}` but marked TBD. No text on ordering, retry, redelivery, ack or dedup.

**Discovery** `[SRC]` https://github.com/cloudevents/spec: "The Registry and Pagination specifications can now be found in the xRegistry/spec repo" (https://github.com/xregistry/spec). The `discovery/` directory no longer exists on `main` (404). `[DERIVED]` Do not bind to CloudEvents Discovery; if we need a catalogue, xRegistry is the successor and our Monitor object can be its own small registry.

## 2. Nostr

**NIP-01** `[SRC]` https://raw.githubusercontent.com/nostr-protocol/nips/master/01.md. Event: `id` (32-byte sha256, lowercase hex), `pubkey`, `created_at` (unix seconds), `kind` (0–65535), `tags` (array of arrays of strings), `content`, `sig` (64-byte schnorr). `id` = sha256 of the serialized array `[0, <pubkey>, <created_at>, <kind>, <tags>, <content>]` with no whitespace and the listed escapes. Relays MUST index single-letter tags (`a-z`, `A-Z`).

Kinds: regular `1000 <= n < 10000 || 4 <= n < 45 || n == 1 || n == 2`; replaceable `10000 <= n < 20000 || n == 0 || n == 3` (latest per pubkey+kind kept; ties → "the event with the lowest id (first in lexical order) should be retained"); ephemeral `20000 <= n < 30000` (not stored); addressable `30000 <= n < 40000` (latest per kind+pubkey+`d` tag).

Client→relay: `["EVENT", <event>]`, `["REQ", <subscription_id>, <filters...>]`, `["CLOSE", <subscription_id>]`; `subscription_id` is "arbitrary, non-empty string of max length 64 chars", managed per WebSocket connection, "not guaranteed to be globally unique". Relay→client: `["EVENT", <subscription_id>, <event>]`, `["OK", <event_id>, <true|false>, <message>]`, `["EOSE", <subscription_id>]`, `["CLOSED", <subscription_id>, <message>]`, `["NOTICE", <message>]`. OK/CLOSED messages use "machine-readable single-word prefix followed by a : " with prefixes `duplicate`, `pow`, `blocked`, `rate-limited`, `invalid`, `restricted`, `mute`, `error`.

**Filter** `[SRC]`: `ids`, `authors`, `kinds`, `#<single-letter (a-zA-Z)>` (list of tag values), `since` (`created_at >= since`), `until` (`created_at <= until`), `limit` (initial query only). "All conditions of a filter that are specified must match" (AND across attributes); within a list "at least one of the arrays' values must match" (OR); multiple filters in one REQ: "events that match any of the filters are to be returned" (OR).

**NIP-42** `[SRC]` https://raw.githubusercontent.com/nostr-protocol/nips/master/42.md: relay sends `["AUTH", <challenge-string>]`; client answers `["AUTH", <signed-event-json>]` with kind `22242`, tags `["relay", <url>]` and `["challenge", <string>]`; prefixes `auth-required:` and `restricted:` on OK/CLOSED.

**NIP-11** `[SRC]` https://raw.githubusercontent.com/nostr-protocol/nips/master/11.md: HTTP GET with `Accept: application/nostr+json` on the WebSocket URL; fields `name`, `description`, `banner`, `icon`, `pubkey`, `self`, `contact`, `supported_nips`, `software`, `version`, `terms_of_service`; `limitation` sub-object: `max_message_length`, `max_subscriptions`, `max_limit`, `max_subid_length`, `max_event_tags`, `max_content_length`, `min_pow_difficulty`, `auth_required`, `payment_required`, `restricted_writes`, `created_at_lower_limit`, `created_at_upper_limit`, `default_limit`.

**What Nostr lacks** `[DERIVED]` from the above: no per-subscriber cursor (only `since`/`until` by producer timestamp, which is neither monotonic nor per-source), no consumer ack (`OK` acknowledges *publishes*, not deliveries), no redelivery or replay contract, no ordering guarantee, subscription state dies with the socket.

## 3. A2A protocol

`[SRC]` https://a2a-protocol.org/latest/specification/ and the raw source https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md. Version: "**Latest Released Version** `1.0.0`" (the `0.3.0` spec is retained). Clients send an `A2A-Version` service parameter (HTTP header `A2A-Version`); empty is interpreted as `0.3`.

**Method names — correction to the brief.** In 1.0 the JSON-RPC `"method"` strings are the binding-independent operation names, verbatim from §9.4: `SendMessage`, `SendStreamingMessage`, `GetTask`, `ListTasks`, `CancelTask`, `SubscribeToTask`, `CreateTaskPushNotificationConfig`, `GetTaskPushNotificationConfig`, `ListTaskPushNotificationConfigs`, `DeleteTaskPushNotificationConfig`, `GetExtendedAgentCard` (§9.3 shows the template `"method": "category/action"`). The `message/send`, `tasks/get`, `tasks/resubscribe`, `tasks/pushNotificationConfig/set` names are 0.3 and are **not** in the 1.0 file (grep returns none). One rendered fetch reported `a2a_sendMessage`; the raw file does not contain that string — `[FALSIFIED]`. REST binding (§5.3): `POST /message:send`, `POST /message:stream`, `GET /tasks/{id}`, `GET /tasks`, `POST /tasks/{id}:cancel`, `POST /tasks/{id}:subscribe`, `POST|GET /tasks/{id}/pushNotificationConfigs`, `GET|DELETE /tasks/{id}/pushNotificationConfigs/{configId}`, `GET /extendedAgentCard`. gRPC rpcs carry the same operation names.

**Objects** `[SRC]`: `AgentCard` (`name`, `description`, `version`, `supportedInterfaces[]` of `AgentInterface{url, protocolBinding, protocolVersion, tenant?}`, `capabilities{streaming, pushNotifications, extensions, extendedAgentCard}`, `skills`, `securitySchemes`, `security`, `signatures`); `Task` (`id`, `contextId`, `status{state, message, timestamp}`, `artifacts[]`, `history[]`, `metadata`); `TaskState`: `TASK_STATE_SUBMITTED`, `TASK_STATE_WORKING`, `TASK_STATE_INPUT_REQUIRED`, `TASK_STATE_AUTH_REQUIRED`, `TASK_STATE_COMPLETED`, `TASK_STATE_FAILED`, `TASK_STATE_CANCELED`, `TASK_STATE_REJECTED`, `TASK_STATE_UNSPECIFIED`; `Message` (`messageId`, `contextId`, `taskId`, `role` ∈ `ROLE_USER`/`ROLE_AGENT`, `parts[]`, `metadata`, `extensions[]`, `referenceTaskIds[]`); `Part` ∈ `TextPart`/`FilePart`/`DataPart`; `Artifact{parts}`; stream events `TaskStatusUpdateEvent{taskId, status}` and `TaskArtifactUpdateEvent{taskId, artifact, final, append, lastChunk}`; `TaskPushNotificationConfig{id, taskId, url, token, authentication: AuthenticationInfo}`. `historyLength`: unset = all, `0` = none, N = cap. Security schemes: APIKey, HTTPAuth, OAuth2, OpenIdConnect, MutualTLS.

**Streaming and durability** `[SRC]`: SSE `Content-Type: text/event-stream`; "The stream MUST close when the task reaches a terminal state"; `SubscribeToTask` "MUST return a `Task` object as the first event in the stream" and supports "A client reconnecting to a task after a network interruption by opening a new stream"; multiple streams per task "MUST receive the same events in the same order". Explicit non-guarantee: "Clients using streaming to retrieve task updates MAY not receive all status update messages if the client is disconnected and then reconnects. Messages MUST NOT be considered a reliable delivery mechanism for critical information." Idempotency: "Get operations are naturally idempotent. Send Message operations MAY be idempotent using messageId detection. Cancel Task operations are idempotent." `[DERIVED]` A2A's durability is *state snapshot on resubscribe*, not *replay from cursor*; the task is the durable object, the stream is not.

## 4. MCP (revision 2026-07-28)

**Extension declaration** `[SRC]` https://modelcontextprotocol.io/extensions/overview and https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning: identifier format `{vendor-prefix}/{extension-name}`, "Identifiers follow the same rules as `_meta` keys, with a mandatory prefix"; official prefix `io.modelcontextprotocol`, third parties use reverse-DNS they own (`com.example/my-extension`). Clients declare in every request's `_meta["io.modelcontextprotocol/clientCapabilities"].extensions`; servers in the `server/discover` result `capabilities.extensions` — shape `"extensions": { "<id>": { ...settings } }`, empty object = supported with no settings. Breaking change → new identifier (`.../my-extension-v2`). Naming of extension methods: no global rule; the Tasks spec models it by *reserving* prefixes: "The `tasks/` method prefix and `notifications/tasks/` notification prefix are reserved for this extension" and "The result-discriminator value `"task"` for `resultType` is reserved". `[SRC]` https://raw.githubusercontent.com/modelcontextprotocol/ext-tasks/main/specification/2026-07-28/tasks.md. `[DERIVED]` Our extension should reserve a method prefix, a `notifications/<prefix>/` prefix, a `resultType` value if any, and a `_meta` prefix, in the same sentence form.

**`_meta` key rules** `[SRC]` https://modelcontextprotocol.io/specification/2026-07-28/basic/index: prefix = dot-separated labels + `/`, reverse DNS; "Any prefix where the second label is `modelcontextprotocol` or `mcp` is reserved"; name `[a-z0-9A-Z]` at ends, `-`, `_`, `.` inside. Required per request: `io.modelcontextprotocol/protocolVersion`, `io.modelcontextprotocol/clientCapabilities`; optional `io.modelcontextprotocol/clientInfo`; response `io.modelcontextprotocol/serverInfo`. `traceparent`, `tracestate`, `baggage` are un-prefixed reserved keys following W3C Trace Context. Every result "MUST include a `resultType`" (`"complete"`, `"input_required"`, extension values). MCP is declared **stateless**: "State that needs to span multiple requests ... MUST be referenced by an explicit identifier the client passes on each request." Servers "MUST NOT initiate JSON-RPC requests". `server/discover` (MUST implement) returns `supportedVersions`, `capabilities`, `instructions`, `ttlMs`, `cacheScope`. `[SRC]` https://modelcontextprotocol.io/specification/2026-07-28/server/discover

**Subscriptions pattern** `[SRC]` https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions: request `subscriptions/listen` with `params.notifications` filter — keys `toolsListChanged` (boolean), `promptsListChanged` (boolean), `resourcesListChanged` (boolean), `resourceSubscriptions` (`string[]` of URIs); "The server MUST NOT send notification types the client has not explicitly requested." First message "MUST" be `notifications/subscriptions/acknowledged` carrying `_meta["io.modelcontextprotocol/subscriptionId"]` (= the JSON-RPC id of the listen request) and the honoured subset of the filter; every notification on the stream carries that `_meta` key. Graceful close = server answers the listen request with `{"resultType": "complete", "_meta": {...subscriptionId}}`. Client cancel = close SSE (HTTP) or `notifications/cancelled` (stdio). "the server holds no subscription state across reconnections" — the client "MUST re-send `subscriptions/listen`". `[DERIVED]` No cursor, no replay, no client ack: MCP subscriptions are at-most-once live streams; durability has to come from the objects notifications describe (as Tasks does).

**Tasks extension** `[SRC]` https://modelcontextprotocol.io/extensions/tasks/overview and the raw `tasks.md` above: id `io.modelcontextprotocol/tasks`, revision `2026-07-28`; only `tools/call` is task-augmentable; server returns `CreateTaskResult` with `resultType: "task"` and a `Task{taskId, status, statusMessage?, createdAt, lastUpdatedAt, ttlMs (number|null), pollIntervalMs}`; statuses `working`, `input_required`, `completed`, `failed`, `cancelled` (last three terminal); methods `tasks/get {taskId}` → `DetailedTask` (adds `inputRequests`, `result`, `error`), `tasks/update {taskId, inputResponses}`, `tasks/cancel {taskId}`; **no `tasks/list`** ("Because there is no `tasks/list`, a server cannot inadvertently leak the existence of one caller's tasks"); task IDs are bearer tokens with "sufficient entropy". Notifications: method `notifications/tasks`, "Each notification carries a complete `DetailedTask`"; subscribed via `subscriptions/listen` with filter key `taskIds?: string[]`, echoed in the acknowledgment. TTL: "servers MAY mark a task as `failed` at any point after the TTL elapses, and subsequently delete it"; `ttlMs` "MAY change over the lifetime of a task". Unsolicited tasks: a task exists only as the result of a client request, and "A server MUST NOT return `CreateTaskResult` to a client that did not include the extension capability" — there is no server-originated task creation `[DERIVED]`.

## 5. Adjacent vocabularies

**Standard Webhooks 1.0.0** `[SRC]` https://raw.githubusercontent.com/standard-webhooks/standard-webhooks/main/spec/standard-webhooks.md: headers `webhook-id`, `webhook-timestamp` (unix seconds), `webhook-signature`; signed content `msg_id.timestamp.payload`; header value `v1,<base64 HMAC-SHA256>` with space-separated multiple signatures for rotation; `v1a` = ed25519 with `whsk_`/`whpk_` key prefixes; verify timestamp "within some allowable tolerance"; `webhook-id` doubles as idempotency key; suggested body `{type, timestamp, data}`. `[DERIVED]` This is the natural sink-side integrity layer for a CE-over-HTTP push, and `webhook-id` ≡ CE `id`.

**W3C PROV-DM** (Recommendation, 2013-04-30) `[SRC]` https://www.w3.org/TR/prov-dm/: types `Entity` ("A physical, digital, conceptual, or other kind of thing with some fixed aspects"), `Activity` ("Something that occurs over a period of time and acts upon or with entities"), `Agent` ("Something that bears some form of responsibility for an activity taking place, for the existence of an entity"); relations `wasGeneratedBy`, `used`, `wasInformedBy`, `wasStartedBy`, `wasEndedBy`, `wasInvalidatedBy`, `wasDerivedFrom`, `wasAttributedTo`, `wasAssociatedWith`, `actedOnBehalfOf`; extended `Revision`, `Quotation`, `PrimarySource`, `Collection`/`hadMember`, `Bundle`, `specializationOf`, `alternateOf`. `[DERIVED]` Alignment: Observation = `Entity`; the monitor run that produced it = `Activity`; the monitor = `Agent` (`wasAttributedTo`); a derived tier (`[DERIVED]` from `[SRC]`) = `wasDerivedFrom`; a State recomputed from observations = `wasDerivedFrom` + `Revision`; a monitor acting for a person = `actedOnBehalfOf`.

**CloudEvents Discovery**: relocated to xRegistry (see §1); no CNCF-CloudEvents discovery document to bind to.

**Kafka** `[UNVERIFIED]` — not fetched in this recon; the "consumer offset + commit" model referenced in our positioning should be cited from the Kafka protocol/consumer docs before the spec binds any wording to it.

## Binding recommendations

(2) CE has no map type: structured provenance (PROV triples) goes in `data`, not in extensions. |

| **Subscription** | CloudEvents Subscriptions 0.1-wip for the object; Nostr NIP-01 for the filter grammar; MCP `subscriptions/listen` for in-session presentation | CE: `id`, `source`, `types`, `filters`, `sink`, `sinkcredential`, `protocol`, `protocolsettings`, manager ops Create/Retrieve/Query/Update/Delete; Nostr: `ids`, `authors`(→ monitors), `kinds`(→ `types`), `#<letter>` tags, `since`, `until`, `limit`, AND-within/OR-across; MCP: `notifications/subscriptions/acknowledged`, `_meta["io.modelcontextprotocol/subscriptionId"]` on every notification, per-request statelessness | **cursor** (`afterSeq` per `source`, or opaque `cursor`) and **ack** (`ackSeq`, cumulative like a committed offset), plus `redeliver`/replay-from-horizon and a durable subscription `id` that survives reconnect (neither CE-Subs, Nostr nor MCP has one); Standard Webhooks headers on HTTP sinks | (1) Two filter grammars: CE dialects `exact|prefix|suffix|all|any|not|sql` are attribute→string maps; Nostr filters are typed arrays with implicit AND/OR. Pick one canonical grammar and define the other as a lossless mapping (Nostr `kinds:[a,b]` ≡ CE `any:[exact:{type:a}, exact:{type:b}]`; `since/until` and `#tags` have **no** CE dialect — they need `sql` or our own dialect). (2) CE-Subs `sink` is push-only; MCP listen is pull-stream; specify both `protocol: HTTP` (CE) and `protocol: MCP` (ours) with the same object. (3) MCP forbids server-initiated requests: ack must be a client→server call, not a server-requested one. |
| **Configure** | MCP Tasks for the request/handle pattern; CE-Subs `config`/`protocolsettings` for the settings bag; A2A `CancelTask` idempotency wording | `config` (Map), `protocolsettings` (Map); a long-running configure returns `resultType: "task"` with `taskId`, `status`, `ttlMs`, `pollIntervalMs`; `tasks/get`/`tasks/cancel` semantics; "Cancel ... operations are idempotent" | our own method names under a reserved prefix (not `tasks/`, not `subscriptions/`); versioned `config` schema (`dataschema` URI); an Observation of `type ...configured` emitted with the new config as `data` so configuration is itself evidence with `tier` | MCP Tasks are client-initiated only; a monitor that reconfigures itself must announce it as an Observation, not as a task. |

**Cross-cutting bindings.** Reverse-DNS everything: CE `type`, MCP extension id and `_meta` prefix, extension method/notification prefixes. Adopt MCP's reservation sentence form. Carry `traceparent` in both the CE extension and MCP `_meta` (same W3C value, both specs allow it). Treat `webhook-id` = CE `id` on HTTP sinks. Tag every observation with a tier; PROV supplies the relation names if we ever serialize lineage as a graph (`wasDerivedFrom`, `wasAttributedTo`, `wasGeneratedBy`, `used`).
